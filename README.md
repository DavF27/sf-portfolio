# Executable Salesforce portfolio

[![CI](https://github.com/DavF27/sf-portfolio/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/DavF27/sf-portfolio/actions/workflows/ci.yml)

Real Salesforce failure modes, reproduced from scratch and **proved by execution**, not described.
Each demo deploys a BEFORE implementation that fails and an AFTER implementation that works, side by side in the same org,
switched from a Lightning panel. On every push to `main`, the CI creates a fresh scratch org, deploys, runs the Apex tests,
runs every demo, records the panel with Playwright and publishes the measurements.

**Live showcase: <https://davf27.github.io/sf-portfolio/>** — recordings, screenshots, measured runs and history,
plus a short video. The cards below are regenerated by the CI after each green run: no number in this README is typed by hand.

## Demos

The cards are measured by the last green CI run.

### [Bulk API all-or-nothing batch](https://davf27.github.io/sf-portfolio/demo/bulk-all-or-nothing.html)

Per-record SOQL/DML in a trigger cascades through two flows; one governor limit fails the **whole** Bulk API batch, valid rows included. Fixed by bulkification and partial success, with the invalid row isolated.

[![Bulk API all-or-nothing batch: measured BEFORE and AFTER](https://davf27.github.io/sf-portfolio/cards/bulk-all-or-nothing.svg)](https://davf27.github.io/sf-portfolio/demo/bulk-all-or-nothing.html)

### [Trigger vs flow order of execution](https://davf27.github.io/sf-portfolio/demo/order-of-execution.html)

An after-save flow runs after the trigger that archives a snapshot: saves succeed, yet snapshots are empty. Fixed with a before-save flow, which also saves a DML.

[![Trigger vs flow order of execution: measured BEFORE and AFTER](https://davf27.github.io/sf-portfolio/cards/order-of-execution.svg)](https://davf27.github.io/sf-portfolio/demo/order-of-execution.html)

### [Silent asynchronous chain](https://davf27.github.io/sf-portfolio/demo/async-chain-break.html)

A chain of queueables stops on one bad line without any error, leaving the rest pending forever. Fixed with bounded bundles and a Transaction Finalizer that logs the failure.

### [Batch Apex: filter in Apex vs in SOQL](https://davf27.github.io/sf-portfolio/demo/batch-filter.html)

[![Batch Apex: filter in Apex vs in SOQL: measured BEFORE and AFTER](https://davf27.github.io/sf-portfolio/cards/batch-filter.svg)](https://davf27.github.io/sf-portfolio/demo/batch-filter.html)

### [Org drift and deployment guard](https://davf27.github.io/sf-portfolio/demo/drift-guard.html)

A hotfix made directly in the org is overwritten by the next deployment. Tooling API hashes are compared with the last deployment tag; an UNKNOWN drift blocks the deployment.

[![Org drift and deployment guard: measured BEFORE and AFTER](https://davf27.github.io/sf-portfolio/cards/drift-guard.svg)](https://davf27.github.io/sf-portfolio/demo/drift-guard.html)

A calibration demo (`Limits_Probe`) validates the measurement chain: it breaks the 100-query limit on purpose and proves that
the failure is still measured.

## How it works

- **BEFORE and AFTER coexist.** A `Demo_Setting__mdt` record per demo and a `DemoStrategy` interface select the implementation;
  the panel and the scripts pass the mode explicitly. The BEFORE code is an intentional, isolated anti-pattern.
- **Measurements survive failures.** A `LimitException` cannot be caught and rolls back everything. Each step publishes a
  `Demo_Step__e` platform event (_publish immediately_), which an event trigger turns into a `Demo_Run__c` record. The panel
  follows the same events in real time through `empApi`.
- **Proof by the CI.** Apex tests assert the BEFORE failure and the AFTER success. `scripts/run-demos.js` and
  `scripts/bulk-demo.js` run each demo in the scratch org (including a real Bulk API 2.0 job) and export `metrics.json`;
  Playwright records the panel; `tools/` proves the deployment guard on a hotfix made outside Git.
- **Synthetic data only**, generated by script with a fixed seed. No customer code, data or names.

## Run it

```bash
npm ci
npm run lint && npm test                     # ESLint, Jest (LWC), node:test (scripts and tools)
sf org create scratch --definition-file config/project-scratch-def.json --alias demo
sf project deploy start --target-org demo
sf org assign permset --name Demo_Admin --name Demo_Bulk --name Demo_Order --name Demo_Async --name Demo_Batch --target-org demo
node scripts/run-demos.js --target-org demo --out scripts/out
node tools/drift.js --target-org demo        # freshness and drift report
```

Then open the **Demo Panel** tab. CI setup (JWT, scratch org signup): [docs/ci-setup.md](docs/ci-setup.md).
